gobot
=====

The TorilMUD helper bot Katumi and the [TorilEQ](https://www.grokh.com/torileq/) item search. They use two SQLite databases: Kegor's `TorilDB.db` for item and mob stats, read-only, and the bot's own `toril.db` for characters and accounts, boots, and load reports.

## How it works

`tt++ katumi.tin`, run in the bot folder (`/srv/bot`), logs in to torilmud.com and calls `gobot` for each event: `-time <uptime> -seen <when>`, `-who` and `-online <n>` every 30 seconds to track boots, who's online and how many, `-char <name> -tell "<text>"` for each tell, `-bak` once each midnight, in the game or not, and `-loginalert` if it stops logging in. If the connection drops or a connect fails, it logs back in 5 seconds later, and while the MUD is down, tintin tries each connect again every 2 seconds for up to 6 minutes (`CONNECT RETRY`), so after a reboot Katumi is back within seconds of the MUD taking logins. MUD text is escaped for the shell by `shellsafe`, and replies go back to the MUD as commands, so keep tintin++ syntax out of them (`tellSafe` in `tell.go`, which every reply line goes through; `tintinSafe` also drops `@` from `TorilDB.db` text).

`login` answers the MUD's prompts one at a time: the account when it asks for one, the password only at the password prompt, and the character at the menu. When the MUD garbles the first line, as it sometimes does right after a connect, it just asks for the account again. After three tries at the account, or a minute without reaching the menu, Katumi drops the connection and logs back in. If the MUD turns the password down twice, Katumi stops logging in, since trying again could only lock the account, and sends an alert (below): put the right password in `tokens.tin` and restart tintin. The 30-second `time` and `who` start once the character is in, so nothing else reaches the MUD during a login. If the MUD says the character doesn't exist, Katumi drops the connection and logs back in, but only until the first `time` answer shows she's in the game, since after that the same words said on a channel would knock her offline.

Tells are matched before any other trigger (priority 4). tintin fires only the first action that matches a line, so a tell that quotes another trigger's words, such as that "doesn't exist" line, would otherwise go to that trigger and never be answered.

Katumi's logs are in `logs/`. tintin writes each session's to `Katumi.<date>.log`, named for the day its login began, with each line stamped with the server's local time (`#log timestamp`), and each tell and reply, dated, to `tells.log`. `bot.log` is gobot's: one line per entry of at most 1,000 bytes, with any control characters a tell or a pasted list carried turned to spaces. tintin writes there too, in a line that starts `tintin:`, for what only it sees: when it starts and quits, each connect, login and drop, and a login that goes wrong (the MUD asking for the account again and again, a login that stalls, a character the MUD says doesn't exist, a password turned down twice). A run of failed connects gets one line, and the connect that ends it says how many failed. A run of gobot that ends early says why there, under its flags, as in `gobot -online: database is locked`: a fatal error, flags it doesn't take (as when `katumi.tin` is newer than the gobot installed), or a bug, with where in gobot it happened. Anything else gobot prints on stderr, like a bug's stack trace, goes only to tintin's screen.

`-who` keeps each character's level and when it was last seen, from the who list, and its class and race when the list shows new ones (`who.go`). A character toril.db doesn't have yet, or one whose class or race has changed or whose level has fallen, as when a character is deleted and someone makes another of the same name, also gets a `who <name>`, whose line shows the account: gobot adds the character, or moves it to that account. `katumi.tin`'s trigger takes that line to its end, and gobot reads the last account on it, past a light flag if one follows, so an account written earlier in the line can't stand in for the MUD's own. A line whose account can't be read adds nothing and is noted in the log. Text in the race's place that names no race in toril.db's `races` table, like a flag after it, is left alone. Like every write, a check waits up to 5 seconds while another process holds toril.db. One that would wait longer saves nothing, and the next check, 30 seconds later, makes up for it.

`-online` takes the count from who's "Total players online" line and adds it to its UTC hour in toril.db's `online` table (`online.go`): the who checks that hour, their total, and the fewest and most at once, so an hour's average is `total / checks`. Its history from May 2013 on came from Katumi's session logs, timed by the MUD's own clock read as US Eastern time; that clock has run up to about 40 minutes slow, so those hours can be off by that much. The table is only in the bot's own `toril.db`: `dbcopy.sh` leaves it out of the copies it publishes.

`-time` takes the MUD's uptime, and `-seen` the second tintin saw it (Unix time). Seen less uptime is when the MUD came up, and every check of a boot gives that start to within a second or two, however long the check waits to run: tintin runs each in the background, and when the MUD lags it answers several at once, so they can be written in any order. A check whose start is nearer the current boot's start than where the boot was last seen, half its uptime later (10 seconds at least), is that boot's. One that starts later is a new boot: a reboot the bot is around for, one while it was away, or each boot of a crash loop. Half the uptime, not a fixed slack, because the MUD's uptime gains or loses up to about 6 seconds a day on the server's clock, while some reboots are back within seconds of Katumi's last check. A boot keeps the highest uptime its checks give, so a check written after a newer one changes nothing: gobot notes it in the log, as it does a check seen before the current boot began, held up past a reboot. A newer check that gives an earlier start moves the boot's start back to it, which puts it right when the boot's first check was seen late. Without `-seen`, gobot uses its own clock.

When `-time` sees a new boot, gobot sends a reboot alert to the [ntfy](https://ntfy.sh) topic whose URL is on the first line of `ntfy.url` in the bot's folder, ex. `https://ntfy.sh/<topic>`. Subscribe to that topic in the ntfy app to get the alerts. Anyone who knows the topic can read them and send their own, so give it a long random name. To check the alerts without waiting for a reboot, run `gobot -testalert` in the bot's folder: it sends a test alert the same way, and if that fails, says why on stderr and exits 1. `gobot -loginalert`, which `katumi.tin` runs when the MUD turns the password down twice, sends one saying Katumi has stopped logging in.

Tells: `stat`, `astat`, `fstat`, `mstat`, `who`, `clist`, `char`, `find`, `class`, `name`, `addname`, `delalt`, `addalt`, `hidden`, `lr`, `lrdel`; `tell katumi help <cmd>` explains each. `stat` and `astat` answer with Kegor's own short and long stats. Items that share a name, which he numbers (a longsword 1 to 3, or a black dagger and a black dagger 2), come back together, up to 10, the closest match first, but a name that ends in a number gets that item alone (`stat longsword 2`). `fstat` and the website search his `eq` table by stat, resist, slot, effect, flag, where an item comes from, who can use it, type and zone, mapped from the names players use in `items.go`, and `fstat` by weapon type too. Armor class is one stat, `ac`, as `stat` shows it: Kegor keeps an item's own armor value apart from its Armor affect, and long stats show both (`AC:3 Armor:-1`), but short stats combine them (`AC:4`), so `ac` and the form's Armor Class search the combined AC (`acSQL`), and `armor` means the same. `fstat` lists 10 items, the most of the first stat compared first, then says how many more there are, with a TorilEQ link to all of them. The link spells its operators as words (`?fstat=dam+gt+2,+slot+neck`), so it needs no escaping in tintin or the MUD. `fstat` reads a search the way players write one (`fstat.go`): commas with or without spaces, `hp=10` as well as `hp = 10`, a stat by its column or full name (`max_str`, `max strength`), a slot by the words players use (`ears`, `ring`, `belt`), and a stat, resist, slot, effect or flag named alone (`maxagi`, `face`, `no_sum`), where a stat alone lists the items with any of it, the most first. A resist can be compared like a stat (`resist fire < 0`). A field it can't read stops the search: the reply names it, and offers a guess when there's a fair one, such as a typo fixed, commas put back, or `stat` for an item's name. The link holds the search as `fstat` read it. `mstat` answers from his `mobs` table (`mobs.go`): his short stats for the mob, the eq he lists it carrying, and its quest's items. Mobs that share a name, which he numbers (the bartender 1 to 20), come back together, up to 10. `astat` adds a line naming up to 5 mobs that carry the item: first those whose eq lists name it, in any case, then, for an item he numbers, those whose lists give the name the game shows, without his number (`a short sword` for `a short sword 2`), as most of his lists do. Those count only where the zones tell the items of that name apart: the mob's zone shares a zone with the item's, and with no other item's of that name, numbered or not. A compound zone such as `Silverymoon - Westgate` shares either part. A mob where two of them load could carry either, so it's left out. `clist` lists an account's visible alts, highest level first, from the account's name or one of its visible characters'. A class, a level, or both after the name list only the alts that fit, in either order: `clist rynshana cleric`, `clist rynshana 50`, `clist rynshana necro 45+`, `clist rynshana 40-50 war`. The class can be named any way `class` takes one. If none fit, the reply says so, as in `@<account> has no level 50 Cleric.` A name that is one account's and another account's character lists both accounts. `class` is for filling a group slot: `class cleric` (or `cle`, or `cler`) lists the accounts online with a level 50 cleric, one line each, with the character its player is online as and those clerics, the accounts already on one first. It leaves out hidden alts, the asker's own account, and the other side of the racewar from the asker's character, going by race. Half-orcs play on both sides, so they're listed for either, and a half-orc asker sees both. A tell Katumi can't make out gets a guess at what was meant (`guess.go`):
- a mistyped command gets the command it's a typo of (`stats` is `stat`)
- a command with nothing to look up gets that command's help
- a `stat`, `astat` or `mstat` that finds nothing gets up to 3 names that match once each word in no name is read as a typo of the closest word that is

Guesses are only ever offered, never run, since some commands change what Katumi keeps. A reply sends the MUD at most 3,000 bytes (`maxReplyBytes` in `tell.go`), because the MUD disconnects a character that sends it more than about 4 KB at once. A longer one, like a `clist` of an account with dozens of alts, ends with a count of the tells left out. A `clist` with no class or level that gets cut short also says how to add one.

The website is `gobot -port 8080` (`torileq.service`, behind nginx, which has to proxy to `127.0.0.1:8080`: gobot listens there only), reading the `TorilDB.db` in its own folder. Its item name box finds names the way `stat` does: as typed, anywhere in a name, or failing that, the words in that order with anything between them, or failing that, every word in any order, so `destruction sword` finds a black longsword of destruction there too. Its searches work by GET as well as by the form's POST, so each results page links to its own search, and `?fstat=<search>` runs an fstat search there, which is where `fstat`'s links go. Results can be ordered by either attribute, or by worn slot in the order of the form's Worn Slot list. A list pasted into the page gets the long stats of each item on it: the output of inventory, equipment, a bag, storage, glist, a shop's list or auction list, each kind of line read by its own pattern in `paste.go`. Lines that name no item, like prompts, headers, table borders and what a wrapped line of auction list leaves on lines of its own, are left out, and a shop's item is also found under its name with a small first letter, or a drink under its container. `-glist` reads its lines the same way. Other flags: `-item` (`stat`'s closest match alone, without the items that share its name), `-glist` (items missing from `TorilDB.db` or last identified before 2020-11-01), and `-checkitems <file>`. The site logs to `logs/bot.log` in its own folder, as the bot does.

The site's build designer, `/torileq/build` (`build.go`, `html/build.html` and `html/build.js`), dresses a character in items from `TorilDB.db`, one to each slot of the game's equipment list, in its order, and totals each set's stats, resists, effects and weight side by side: up to four sets, each after the first showing how it differs from the first, in green where it's better and red where it's worse (saving throws are better less). Armor Class is the AC `stat` shows (`acSQL`). A slot's box finds an item the way the search's name box finds one, but only among the items Kegor lists for that slot, unless it holds an item's exact name. As a box is typed in, `build.js` offers the names that fit, with their stats, from `/torileq/build/names`, and sends each change, putting the page that comes back in place of the old one. Without the script, the page's buttons do the same. Each change is posted, and answered with a redirect to the build's link, which holds the character and each item by its full name, so the address bar always holds the build, ready to pass on. A list pasted from `equipment`, or from `look` at someone, fills a set: a second `<worn in ear>` goes in the second ear, `<wielding twohanded>` is the primary weapon and `<held in both hands>` the held slot. With a class, race, alignment or sex chosen, the designer warns of items the character can't use, by their `item_flags` and the classes their `usable_by` names, and offers only names it can use. Where Kegor's short stats sum restrictions up differently (`BLACKGUARD/HEXBLADE/WARRIOR-ONLY`), it follows TorilMUD's builder docs (the Obj-File page of the torilmud/docs wiki): hexblades share the rangers' ANTI- flag and battlechanters the bards', half-orcs can't use an item barred to humans or to orcs, NO-THIEF may or may not bar bards and battlechanters, so it says they may not, and only yuan-ti have a tail. It also warns of more than two hands in use (a two-handed item takes both), a two-handed weapon as the secondary, an item Kegor lists for another slot, and an item covered by a whole-body item on the body (the arms and legs) or a whole-head item on the head (the eyes and face), as players' equipment lists show them. An item it warns of still counts in the totals. A request matches at most 30 names loosely (`maxLoose`), since each loose match reads the whole `eq` table, and a link can hold 104 names.

The designer's Fill (`best.go`) fills a set with the items that give the most of a stat or resist, or the least of a saving throw: the most any set of items can give, not the best item for each slot on its own, so a whole-body suit is weighed against a body item with arms and legs, a whole-head helm against a head item with eyes and face, and each way of filling two hands against the others. A second stat breaks its ties and fills the slots the first leaves empty, then the lighter items win, and a slot that would add nothing stays empty. The hands can be kept to a weapon and a shield, two weapons, a two-handed weapon, a weapon and a held item, a shield and a held item, or nothing, since it's a class's skills that make a shield or a second weapon worth holding. Rare items, quest rewards and invasion items can be left out, and an item Kegor marks out of the game (load code `!`) or no take (`X`, or `NOTAKE`) never goes in. It uses only items the character can use with no warning at all, so a bard's set has no NO-THIEF item. A class, race, alignment or sex left blank stands for all of them, so the set suits every one, and nothing goes on the tail unless the race is yuan-ti. A fill never picks a part of the character itself: the designer can't tell which classes, races and alignments the game lets go together, and `help paladin` has named different races over the years. Two of an item can fill a pair of slots, since players wear two of the same ring, earring or bracer. With "keeping what's in it", the set's items stay, and count toward the two hands and what a whole item covers. A filled set gets the stat as its label, and the fill's choices are kept in the build's link. A fill reads `eq` once, and takes about 40 ms at most.

`torileq.service` shuts the site in: it runs as `trance`, but can write only `/srv/web/torileq/logs` and can't see `/home`, `/srv/bot` or `/srv/irc`. After changing it:

    sudo cp torileq.service /etc/systemd/system/ && sudo systemctl daemon-reload && sudo systemctl restart torileq
    systemctl status torileq && curl -sI https://www.grokh.com/torileq/ | head -1

## TorilDB.db

`torildb.sh` downloads Kegor's `TorilDB.db` and puts it in the bot's folder, the website's, and `/home/trance/mud/torilmud`, where another character's tintin setup also answers `stat` with gobot. His download link stays out of the repo: put it on the first line of `/srv/bot/torildb.url`. Run the script daily from cron:

    17 6 * * * $HOME/go/src/github.com/grokh/gobot/torildb.sh

It only replaces a copy once `gobot -checkitems` passes the download: the file is whole, has every `eq` and `mobs` column gobot reads, and holds at least 90% as many items as the copy in use. The copy it replaces is kept as `TorilDB.db.prev`. If the check fails, nothing changes, and the reason goes to stderr (mailed by cron) and `logs/bot.log`. If `TorilDB.db` goes missing or can't be read, `stat`, `astat` and `fstat` say item stats are unavailable, `mstat` that mob stats are, and the website answers 503. If only the `mobs` table can't be read, `astat` leaves out its line of mobs. A tell that needs the bot's own `toril.db` when it can't be read, or another process has held it for 5 seconds, gets a reply saying Katumi's records are unavailable, and changes nothing.

New item stats go to Kegor by mwrite, ideally with the zone, the load type, and any quest that uses the item. His load types, in `eq`'s `load` column, are R rare, Q quest reward, S store, I invasion, ! out of game, C common (loads on more than one mob or zone), K key, X no take, and N for most others; C, K and X mostly keep junk out of his zone stats. gobot doesn't read the item tables in old `toril.db` files any more, but the published copy's are filled from `TorilDB.db` (see `dbcopy.sh` below).

## Build and run

You need Go 1.22+ and gcc, since `mattn/go-sqlite3` compiles SQLite into gobot.

    go vet ./... && go test ./...   # needs the sqlite3 CLI
    go install                      # the bot uses it from its next event
    ./publish.sh                    # the website

If tt++ 2.02.20 or later is installed, `go test` also runs `katumi.tin` in it (`Test_Tintin`). Fake tells go through the real tell trigger, `shellsafe` and replies to a gobot built from the checkout, and some try to get a shell command, a tintin command or `$cpw` through. Two quote another trigger's words, and still have to be answered as tells. Fake `who <name>` lines go through the who trigger into a toril.db: a one-digit level, a flag before the account, a light flag after it, and an account written into the line ahead of the MUD's own, which the character mustn't be filed under. Then the script logs in to a stand-in MUD on 127.0.0.1 that is down when tintin starts and then comes up. It has to keep trying while the MUD is down, wait out its relogin delay (cut from 5 seconds to half a second) after a drop, and get through a garbled first line, prompts that come before the answer to the last, an account turned down three times, and a login that stalls (given 5 seconds, not a minute). Each answer has to wait for its prompt and go out once, only the password prompt may get the password, and the ticker, run every 0.2 seconds, may send nothing before the character is in. A second stand-in turns the password down twice, and the script has to stop logging in. `katumi.tin`'s lines in `bot.log` have to give each of those steps, in order, its session log has to stamp its lines with the time, and the stopped login has to send an alert, to a stand-in for ntfy. It never reaches torilmud.com: for the tells, tintin reads a copy of the script without `#session` lines or login events, and for the logins, a copy whose only `#session` line is for the stand-in. `TORILMUD_TIN=/home/trance/mud/torilmud/torilmud.tin go test ./...` checks that script too, logging in with `play ynndchiarhlizz;login` as the server's `basic.tin` does. Its lines in `bot.log` have to give the same steps, less the one for starting, which it leaves to `basic.tin`. It stamps no session log and sends no alert. On Windows it runs WinTin++ with Git for Windows' `sh`, and `go test -short` skips it.

[NyyLIB](https://github.com/Nyyrazzilyss/NyyLIB), the Mudlet package many players use, reads two kinds of line from Katumi with triggers: clist and char replies fill its who list, and the NHC welcome makes it look the newcomer up. `Test_NyyLIB` runs NyyLIB's own trigger patterns against gobot's replies, so a wording change that would break them fails. Tell Nyyrazzilyss before changing those lines on purpose.

GitHub runs the same checks on every pull request and every push to main (`.github/workflows/ci.yml`): `gofmt`, `go vet` and `go test`, on the Go and tintin++ versions the server runs. Those versions are set at the top of the workflow, so update them along with the list at the end of this file. The run fails if `Test_Tintin` skips. It can't check `torilmud.tin`, which is in a private repo.

`publish.sh` stops the site, copies in the binary and `html/`, and always restarts it. The site's `TorilDB.db` is `torildb.sh`'s to keep current, so a new site has none until that has run once. `dbcopy.sh` publishes a copy of `toril.db` to the download and two local folders. Run it nightly from cron, as the server does at 02:02 (`02 2 * * * $HOME/go/src/github.com/grokh/gobot/dbcopy.sh`). The copy starts as an empty database and gets only what `dbcopy_public.sql` lists: visible characters, accounts by name, boots, and the races and classes. Hidden alts, real names, load reports and the `online` table aren't on the list, so they're never written to the copy, and a table or column added to the bot's `toril.db` later stays out until it's listed there. The bot's `toril.db` is opened read-only and read in one transaction, so the bot can keep writing meanwhile, and the copy is an ordinary rollback-journal database whether or not the bot's is in WAL mode. NyyLIB downloads the copy with `@updatedb` and reads item stats from it, so `dbcopy.sh` also fills its `items` and `item_flags` from the bot's `TorilDB.db` with `dbcopy_items.sql`, in the shape NyyLIB reads. A potion, scroll or poison row NyyLIB couldn't read would stop it starting, so the fill fails rather than publish one. If it fails, or `TorilDB.db` is missing, the copy gets the old `items` and `item_flags` from the bot's `toril.db`, if it still has them, and the reason goes to stderr.

`gobot -bak` writes `bak/toril.db.<date>.gz` and keeps 60 days plus the first of each month. It opens `toril.db` read-only, and fails, keeping the day's earlier backup, rather than save a partial dump or one of a database that lacks a table `init_db.sql` makes: a missing or empty `toril.db`, or the published copy `dbcopy.sh` writes to the gobot checkout. The reason goes to stderr and `logs/bot.log`. Each backup it writes gets a line there too, with its size, so the log shows that it ran, and that it ran once.

To restore, move `toril.db` aside, with its `toril.db-journal` if it has one, and run `gobot -res <file>` in the bot folder. It loads the backup into a new database beside `toril.db` and renames that into place only once the file has decompressed whole, the dump has ended in `COMMIT` and loaded without an error, and the result passes SQLite's integrity check and has all of those tables. It won't replace a `toril.db` that has tables. An empty one, which gobot makes when it runs while `toril.db` is away, is fine. It prints what it restored, or why it didn't.

`sqlite3 toril.db ".read init_db.sql"` builds a new database. Not in the repo: `toril.db`, `TorilDB.db`, `torildb.url` (Kegor's download link), `tokens.tin` (the bot's `acct`, `char`, `cpw`), and `ntfy.url` (the ntfy topic for reboot alerts). Two one-time scripts are in the repo's history, not its files: `fix_times_and_stats.sql`, which moved the stored times to UTC in November 2026, and `conv.sql`, the 2013 schema conversion.

Currently running on Debian 13, Tintin++ 2.02.61, and Go 1.27.2, with SQLite 3.54.1 built into gobot (mattn/go-sqlite3 v1.14.53) and the sqlite3 3.46.1 CLI for backups and `dbcopy.sh`.
